## `useMutationFlow` で何が変わるか

これを使わない場合、pending の状態と閉じるかどうかの判断を自分で手動管理する
ことになります。このフックは **pending**——トリガー時に true、ハンドラーが
完了したらクリア——を管理してくれるので、自前で真偽値を管理する代わりに
`submit.pending` で入力を無効化できます。それ以外はすべてあなたのものです。
ハンドラーが閉じるかどうかを決め（`call.end(value)` を呼ぶか呼ばないか）、
自分でエラーを処理します。フックが例外に触れることはありません。

「**保存を失敗させる**」にチェックを入れて送信すると、その動きが見られます。
ハンドラーは `call.end()` をスキップし、フックが pending をクリアし、入力欄は
値を保持したまま、ダイアログは再試行できるよう開いたままになります。

## 使いどころ

- リクエストが進行中の間、送信ボタン自身を無効化したい場合。
- 「失敗時は開いたまま」という挙動——ユーザーが入力した内容を失うべきではない
  場合。
- ハンドラーが Callable 側ではなく**呼び出し箇所**で提供される場合。これに
  より、二つの異なる呼び出し元が同じフォームに対して異なる mutation を実行
  できます。

## 使う**べきでない**とき

ダイアログの目的が単に値を読み取ることだけ（カラーピッカー、アイテムピッカー
など）であれば、mutation はダイアログの外に置くべきです。呼び出し側は
`const id = await Picker.call(…); await api.delete(id)` のように書きます——
これによってピッカーは純粋で再利用可能なままになります。
