## すべての yes/no が真偽値であるとは限らない

[confirm-dialog](/ja/examples/confirm-dialog) は `boolean` を返し、「進めるか
どうか」にはそれが適切です。同意は事情が異なります。この Callable は
`'allow' | 'deny'` を返します。Response の型自体が API の一部です——名前付き
のユニオン型は呼び出し箇所で自己説明的になり（`result === 'allow'` は `true`
がどちらを指すか覚えておくよりわかりやすい）、将来の拡張の余地も残ります
（`'allow-once'`、`'manage'` など）。呼び出し側をすべて書き換える必要はあり
ません。二つの結果が純粋な真偽ではない場合、あるいはいつか三つ目の結果が
現れることが予想される場合は、`boolean` を超えて考えましょう。

Response の集合は、ユーザーがどのように離脱できるかも決めます。ここには意図
的に背景クリックや Esc のハンドラーがありません。`'allow' | 'deny'` には
「閉じられた」というバリアントがないため、答えずにプロンプトを閉じる方法も
意図的に存在しません。[item-picker](/ja/examples/item-picker) と比較して
みてください。そちらの `T | null` の Response は**閉じる**という状態を実際に
モデル化しているので、クリックして離れることを許しています。Response の型と
用意する離脱手段は一致していなければなりません。

## 使いどころ

OAuth 風の同意、権限や Cookie のプロンプト、「これらの条件に同意する」といった
フロー——結果が使い捨ての yes/no ではなく、保存・記録・分岐の対象になるラベル
付きの決定であるあらゆる場面に使えます。
